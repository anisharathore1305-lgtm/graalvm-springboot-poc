# 03 - My First Native Image Failure

## "The Build Succeeded... So We're Done, Right?"

After getting my first successful native build, I thought the difficult part was over.

The build had completed.

`poc.exe` was sitting inside my `target` directory.

The application was ready to run.

So obviously, I did what any developer would do:

```cmd
target\poc.exe
````

And then...

💥

The application crashed.

So much for being done. 😂

---

## The Error

The error I got was:

```text
java.lang.IllegalArgumentException:
Unable to instantiate factory class
[org.springframework.boot.webmvc.WebMvcWebApplicationTypeDeducer]
```

And further down:

```text
Caused by:
java.lang.ClassNotFoundException:
org.springframework.boot.webmvc.WebMvcWebApplicationTypeDeducer
```

At first glance, this looked like a pretty straightforward problem.

The application couldn't find a class.

But there was something strange about it.

I knew this was a Spring Boot class.

So the first question became:

> **"Does this class even exist in my application dependencies?"**

---

## Is the Class Actually Missing?

Instead of immediately changing configuration randomly, I decided to verify whether the class actually existed.

I inspected the Spring Boot dependency JAR.

And...

**The class was there.**

The JAR contained:

```text
org/springframework/boot/webmvc/WebMvcWebApplicationTypeDeducer.class
```

So now I had a slightly confusing situation:

```text
Spring Boot dependency
        ↓
Class exists ✅

Native executable
        ↓
ClassNotFoundException ❌
```

The class wasn't missing from the dependency.

So why couldn't the native executable find it?

This was the point where I realized that Native Image was doing something very different from simply taking my JAR and converting it into an `.exe`.

---

## Looking Into Spring AOT

The next thing I investigated was the output generated by Spring AOT.

Inside the native build output, I found generated reachability metadata.

One of the entries specifically referenced the class that was failing:

```json
{
  "type": "org.springframework.boot.webmvc.WebMvcWebApplicationTypeDeducer",
  "allDeclaredConstructors": true
}
```

That was interesting.

Spring AOT knew about the class.

The class existed in the dependency.

The metadata even referenced it.

Yet the native executable still failed with:

```text
ClassNotFoundException
```

So I started looking deeper into how the Native Image build was actually being assembled.

---

## Looking at the Native Image Arguments

I inspected the arguments being passed to `native-image`.

That's when I found something even more suspicious.

The native build was being given several configuration directories containing reachability metadata.

And some of those metadata entries appeared to belong to **different dependency versions** from the ones actually present in my application.

For example, the native build was using metadata related to versions such as:

```text
spring-context 5.3.15
spring-web 5.3.18
spring-aop 6.1.0
spring-expression 6.2.7
spring-boot-web-server 4.0.2
spring-boot-servlet 4.0.6
tomcat-embed-core 11.0.18
aspectjweaver 1.9.7
aspectjrt 1.9.6
```

But my actual application was using a different dependency set, including:

```text
Spring Boot 4.1.1
Spring Framework 7.0.9
Tomcat 11.0.24
AspectJ 1.9.25.1
```

That immediately raised a red flag.

The application dependencies themselves looked correct.

But the Native Image build was also consuming reachability metadata, and some of the metadata being picked up was clearly not aligned with the versions actually being used.

---

## And Then I Found Another Clue

During the native build with GraalVM 21, I had also noticed this warning:

```text
Warning: Found typeReached condition in JSON configuration files.
The typeReached condition is not supported by this version of GraalVM
and will be considered as always true.
Please consider upgrading to the latest GraalVM version
to be able to use all the latest features.
```

At first, I didn't fully understand how important this warning was.

But now it started making more sense.

Maybe the problem wasn't only my application.

Maybe the versions of **Spring Boot, Spring AOT metadata, Native Build Tools, and GraalVM** were not aligned.

So instead of trying to patch the `ClassNotFoundException` blindly, I stepped back and checked the compatibility requirements.

---

## Checking the GraalVM Version

At that point, I was using:

```text
GraalVM 21.0.12
```

My Spring Boot version was:

```text
Spring Boot 4.1.1
```

I checked the Spring Boot documentation for the Native Image requirements.

And there it was.

For Spring Boot 4.1.1, the supported GraalVM Native Image setup requires **GraalVM 25 or newer**.

I had been trying to build a Spring Boot 4.1.1 application using GraalVM 21.

That explained why I was seeing compatibility-related behavior during the native build.

---

## The Fix

I already had a GraalVM 25 installation available, so I switched my environment to:

```text
GraalVM 25.0.4
Java 25.0.4
```

I updated my `JAVA_HOME` and `PATH` so that the command line was actually using the new GraalVM installation.

I verified it with:

```cmd
java -version
native-image --version
```

Then I cleaned the previous native build output and rebuilt the application:

```cmd
mvnw.cmd clean
mvnw.cmd -Pnative native:compile
```

And this time...

The build completed successfully.

More importantly, the earlier `typeReached` warning was gone.

---

## The Moment It Finally Worked

I ran the generated executable again:

```cmd
target\poc.exe
```

And this time:

```text
Starting AOT-processed PocApplication using Java 25.0.4
Tomcat initialized with port 8080
Tomcat started on port 8080
Started PocApplication in 0.102 seconds
```

No crash.

No `ClassNotFoundException`.

The application actually started. 🎉

After all that investigation, the tiny Spring Boot application was finally running successfully as a native executable.

---

## What Actually Happened?

This was probably the most important lesson from my first Native Image failure.

At first, the error looked like:

> **"Spring Boot can't find a class."**

But the class wasn't actually missing.

The dependency contained the class.

Spring AOT had generated metadata referencing it.

The bigger issue was that my native build environment was not properly aligned with the Spring Boot version I was using.

I was using **GraalVM 21 with Spring Boot 4.1.1**, while Spring Boot 4.1.1 expects **GraalVM 25+** for Native Image.

The unsupported `typeReached` warning was another important clue that my GraalVM version was too old for the metadata being consumed.

---

## What I Learned From This Failure

### 1. A successful native build doesn't guarantee a successful application

The fact that:

```text
native:compile
        ↓
BUILD SUCCESS
```

doesn't necessarily mean:

```text
Application starts successfully
        ↓
Everything works
```

Native compilation can succeed while a runtime problem still exists.

---

### 2. Native Image is more than "compile the JAR into an EXE"

There is a lot more happening during the native build.

The build performs analysis of the application and its dependencies and uses information such as reachability metadata to determine what needs to be included and how it should behave at runtime.

That means the native build environment and metadata matter a lot.

---

### 3. Version compatibility matters

I learned this the slightly painful way. 😂

My application dependencies, Spring AOT, Native Build Tools, and GraalVM all need to work together.

Just because two technologies individually support Java doesn't mean every combination of their versions will behave correctly.

---

### 4. Don't blindly trust the first error message

The error said:

```text
ClassNotFoundException
```

My first instinct could have been to manually add configuration for that class.

But the class wasn't actually missing.

Investigating the dependency, generated AOT metadata, native-image arguments, warnings, and version requirements eventually pointed toward the real issue.

That was a much better debugging lesson than simply making the error disappear.

---

## The Bigger Lesson

Until this point, my GraalVM experiment had mostly been about performance:

> **"How much faster can I make my application start?"**

This failure changed the direction of the experiment.

I realized that moving from the JVM to Native Image isn't simply a matter of changing the build command.

It changes some assumptions about how the application is analyzed, what can be discovered at runtime, and what information needs to be available during the native build.

And that raised another question in my mind:

> **"Okay... if Native Image has to know so much at build time, what happens when my application does something dynamically at runtime?"**

Time to break it again. 😈

That led me to my next experiment:

**Reflection.**
